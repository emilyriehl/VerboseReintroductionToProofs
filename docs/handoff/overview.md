# What this project is and how it is built

## The two games

*Reintroduction to Proofs* (Emily Riehl, 2025) is a lean4game: 17 worlds, 159 levels, teaching
proofs and constructions in dependent type theory through Lean tactics (`intro`, `exact`,
`constructor`, `cases`, …). It runs on the public Lean Game Server at Heinrich Heine University
(adam.math.hhu.de), which imports a game from the GitHub Actions artifact of its repository.

This repository is a second edition of the same game in which the player types **Verbose Lean**
sentences (Patrick Massot's controlled English: `Assume h : P`, `We conclude by h`, `Let's prove
that x works`) plus a handful of sentences written for this game for the parts of the curriculum
Verbose does not cover (constructing data: pairs, sums, case analysis, recursion). The thesis of
the original, that elements and proofs follow the same rules, is kept: `Fix` and `Assume`, or
`Let's use` and `We conclude by`, are deliberately parallel.

Both editions present the same mathematics. That is enforced, not hoped for:

- the repository was created from the original's git history, and the original is merged in
  weekly (`sync-upstream` workflow; manual recipe in `maintenance.md` §1);
- `scripts/check_parity.py` (run by the `parity-check` workflow on every push) compares every
  `Statement`, the level lists and the world graph with the original at the commit recorded in
  `UPSTREAM_COMMIT`, and fails on any difference not listed in `parity-allowlist.txt`.

So the division of labour is: mathematics, level structure and tactic-neutral prose are edited in
the original and flow here; proofs, hints that mention sentences, sentence documentation and the
game-side phrase definitions live here.

## Verbose configuration (`Game/Metadata.lean`)

`configureAnonymousCaseSplittingLemmas Classical.em` (so `We discuss depending on whether P or
¬ P` works), `configureHelpProviders …` with Verbose's defaults minus its implication provider
(replaced by a propositions-only wrapper) plus the game's two, `disableWidget` (lean4game cannot
render ProofWidgets) and `disableHelpTactic` (the game supplies its own `help`). Verbose displays
implications as `P ⇒ Q`; the game keeps that (Emily's decision after playing) and tells players
in Implication World that `→` and `⇒` are both accepted.

## The player's vocabulary

The table lists where each sentence is introduced (this is also the `taughtAt` table in
`Help.lean`, which `help` uses to avoid suggesting sentences from later levels) and where it is
implemented. Everything not marked "game" is stock Verbose Lean.

| Sentence | Does | First taught | Implemented |
|---|---|---|---|
| `Let's use e`, `Let's use an assumption` | supply an element or proof for the goal (data twin of `We conclude by`) | Type World 1 | game, `Synonyms.lean` |
| `We conclude by e`, `We conclude by h applied to p` | close the goal with a term | Type World 2 | Verbose; game override adds guidance when `h` is a disjunction/sum/∃ |
| `Fix x : A`, `Fix f b a` | introduce elements | Function World 1 | Verbose |
| `We apply f`, `By h it suffices to prove that P` | backward step through a function or implication | Function World 3 | Verbose |
| `Claim h : P from e`, `Claim h : P by …`, nameless `Claim P from e` | intermediate fact (Verbose's `Fact`, renamed; `Fact`/`We know` are not offered) | Implication World 4 | game, `NamedPhrases.lean` + `Synonyms.lean` |
| `Assume h : P`, `Assume that P`, `Assume (p : P) (q : Q)`, `Assume h : _` | introduce hypotheses | Implication World 5 | game copy of Verbose's scoped phrase; `Assume that` override names the hypothesis sensibly |
| `Let's construct the pair`, `Let's construct it componentwise` | split a structure goal (`×`, `Σ`, `≃`, …) into components | Product World 1 / Equivalence World 1 | game, `Construct.lean` |
| `By p we get a : A and b : B`, `By h we get x such that …`, `By h we get (hp : P) (hq : Q)` | destructure a pair, conjunction or existential | Product World 4 | game synonyms + Verbose |
| `Set x : A := e` | local definition (Lean's `let`; Verbose's `Set` misbehaves on data goals) | Product World 9 | game override |
| `Let's first prove that P`, `Let's now prove that Q` (`_` allowed) | split `∧` / `↔` | Conjunction World 1 | Verbose |
| `Let's construct an element of A` | choose the summand of `A ⊕ B` | Coproduct World 1 | game, `Construct.lean` |
| `Let's consider all cases for x`, `Let's first/next/now consider the case where x is c args` | case analysis on `Bool`, `⊕`, `ℕ`, `×` data or a `∨`/`⊕` hypothesis; unannounced cases display as "You need to announce: …" | Coproduct World 4 | game, `Cases.lean` |
| `Let's prove that P` (goal `P ∨ Q`) | choose a disjunct | Disjunction World 1 | Verbose |
| `We proceed using h` | case split on `h : P ∨ Q` or `s : A ⊕ B` | Disjunction World 3 | Verbose; game override adds sums |
| `This is impossible because of e` | eliminate `e : Empty`, `h : False`, `h applied to p` with `h : ¬P`, or an impossible equation like `false = true` | Empty World 1 | game, `Construct.lean` |
| `Let's prove it's contradictory` | `exfalso` | Negation World 5 | Verbose |
| `Assume for contradiction h : ¬ P` | proof by contradiction | Classical World 1 | game copy of Verbose's scoped phrase |
| `We discuss depending on whether P or ¬ P` | excluded middle | Classical World 3 | Verbose |
| `We conclude by rfl` | definitional equality | Equality World 1 | Verbose |
| `We rewrite using h`, `← h`, `at h'`, `everywhere` | rewrite; never auto-closes with `rfl` (like the original's `rw`) | Equality World 4 | game override |
| `Let's prove that x works` | existential witness | Quantifier World 4 | Verbose |
| `By funext it suffices to prove that ∀ x, f x = g x` | function extensionality (`funext` is a `NewTheorem` there) | Advanced Function World 13 | Verbose |
| `We compute`, `We compute at h` | arithmetic normalisation; splits conjunctions first; disabled in Natural Numbers World 7–10 where it would solve the induction exercises | Natural Numbers World 2 | game override |
| `Let's prove by induction that ∀ n, P n`, `Let's prove by induction H : …`, `… that _` | induction, statement may be the goal (`_`) | Natural Numbers World 3 | game override (Verbose's minus a `simp_rw` that closed trivial base cases early) |
| `Let's define it by recursion on n` (+ `Fix r : C k` in the `succ k` case) | recursion for data | Natural Numbers World 4 | game, `Cases.lean` |
| `help` | lists sentences that apply now, filtered to those already taught; otherwise "No suggestion yet" | always | game, `Help.lean` |

Verbose sentences the game never teaches (`Since … we get`, `We combine`, `Calc`, `Fact`) are
never suggested by `help`; some still parse. Reserved words to remember when writing Lean in
level files: once Verbose is imported, `and`, `or`, `to`, `is`, `on`, `as`, `for`, `we`, `by`,
`the`, `it`, `that`, `such`, `We`, `Fix`, `Set`, `By`, `Since`, `Claim`, `Assume`, `Let's`, … are
tokens; write `Bool.and x y` or `x && y`, and quote tactic words in inventory lines (`«apply»`).

## Inventory mechanics (why every word needs declaring)

lean4game's server checks a proof against the player's unlocked inventory **word by word**: it
records every alphabetic atom of the proof as a "tactic" (except a short stop list) and, at
difficulty 2 ("regular"), rejects any word not unlocked. Verbose sentences split into many
atoms, so the game declares the leading words as tiles (`NewTactic «We» «Let's» «Fix» …`) and
the rest as hidden words (`NewHiddenTactic «conclude» «by» «that» …`). Hidden words still need
a `TacticDoc` to exist in the inventory at all. Consequences:

- a tile is named after a leading word (`We`, `Let's`, `By`, `Claim`, …) and its `TacticDoc`
  lists the sentences that start with it;
- `DisabledTactic «compute»` can switch off a sentence by one of its words;
- `Prop`, `Type`, `match`, `fun` are "words" and are declared;
- a sentence is "taught" at the level whose `NewTactic`/`NewHiddenTactic` lines first introduce
  its words, and `Help.lean`'s `taughtAt` table must agree with that;
- the stock tactics (`exact`, `apply`, …) are not declared, so players cannot type them.

The dev client does not send the player's inventory (relay falls back to difficulty 1), so
`run_level.py` at difficulty 2 and adam are the places where the word check really bites.

## Design decisions and their reasons

All in `notes/PORT_NOTES.md` (chronological) and `notes/SPIKE_FINDINGS.md`; the ones that shape
the code:

- **Overrides rather than forks.** Where Verbose's behaviour did not fit the levels, the game
  declares a higher-priority sentence with the same text (`Overrides.lean`), each with a
  comment saying why: `We rewrite using` without the trailing `rfl` attempt (transparency
  surprises); `We compute` splitting `∧` first; induction without `simp_rw`; `Set` via `let`;
  `We proceed using` for sums; `Assume that` naming; `We conclude by` guidance messages.
- **Scoped phrases copied globally** (`NamedPhrases.lean`): lean4game parses the player's
  document before re-applying the level's `open`s, so `scoped` syntax is invisible to players
  (lean4game issue draft in `notes/`).
- **Construction vocabulary** (`Construct.lean`, `Cases.lean`): designed with Emily in
  `notes/CONSTRUCTION_VOCABULARY.md`; the case sentences name constructor fields in the
  announcement and accept cases in any order; unannounced cases are shown as a blocker goal
  "You need to announce: …" (Verbose's style).
- **Level-aware `help`**: the inventory cannot express "already taught", so `Help.lean` has a
  static table and reads the world graph from the built game data; the current level is read
  off the imported module name.
- **Parity over convenience**: where Verbose forced a different Lean spelling (`Bool.and`), the
  statement difference is allow-listed rather than the original changed.

## How it was tested

- 253 recorded inputs replayed through the server's own `Runner` at difficulty 2
  (`scripts/replay_all.py`), after every build.
- A headless-Chrome playthrough of all 158 levels through the real client and relay
  (`scripts/ux-tests/playthrough.mjs`), plus spot checks against adam.
- Emily played every world herself on the local dev server (two rounds on the spike, one full
  playthrough of the port); her findings and the resulting changes are in `notes/UX_NOTES.md`
  and `notes/SPIKE_FINDINGS.md`.
