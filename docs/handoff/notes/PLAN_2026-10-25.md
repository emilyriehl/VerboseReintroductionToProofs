# Verbose Reintroduction to Proofs: assessment and setup plan

## Context

`emilyriehl/ReintroductionToProofs` is a lean4game (GameSkeleton) project on Lean `v4.23.0`
with Mathlib already required, hosted on adam.math.hhu.de via the standard GitHub-Actions
artifact import. The goal is a second, publicly playable game with the same mathematics whose
player-facing language is Verbose Lean (controlled English) instead of Lean tactic names, a
possibly reimagined web UX for people who know no Lean, and a mechanism so that improvements to
the original keep flowing into the verbose version. The original game and its hosting must not be
disrupted, and nothing in the original repo is edited without explicit permission.

Everything below was established read-only: repo inventory (17 worlds, 159 level files, 361
hints), the local `GameServer` source in `.lake/packages/GameServer`, Verbose Lean sources at tag
`v4.23.0` and `master`, lean4game docs and relay source, and the one existing precedent that
combines the two (`Chr0mium24/math-atlas-lean`).

**Ground rules agreed with Emily:**
- Everything lives under `github.com/emilyriehl`: the new game repo and any temporary fork of
  `verbose-lean4`. Emily creates the repos (or approves a `gh repo create` run from here); no
  push to GitHub happens without her approval.
- Nothing in `ReintroductionToProofs` is edited without separate, explicit permission.
- Contributions to `PatrickMassot/verbose-lean4` (the `gameExt` rename, later any new phrases):
  I prepare the patch, branch and a draft description locally; Emily reviews, commits, pushes and
  opens the PR herself. Commits for those PRs are hers, so attribution lines are her decision.

## Part A: Answers to the three questions

### A1. Is it a good idea? Coverage and incompatibilities

**Verdict: viable, and no fundamental incompatibility, but it is partly a language-design
project, not a mechanical port.** The decisive fact is that about a third of the game builds
*data*, not proofs: 55 of 159 levels have goals like `B`, `A × B`, `A ⊕ B → C`, `A ≃ B`,
`Type` (TypeWorld, FunctionWorld, ProductWorld, CoproductWorld, EmptyWorld, EquivalenceWorld,
DependentWorld), plus ~5 Bool/ℕ levels whose witness is a function defined by cases. Verbose Lean
is designed for propositions and its vocabulary ("Let's prove that", "Since … we get",
"We conclude by") has no construction register.

**Coverage of the game's tactic inventory by stock Verbose (v4.23.0, English):**

| Game tactic (levels using it) | Verbose phrase | Status |
|---|---|---|
| `intro` (108) | `Fix x : A` for data, `Assume h : P` for hypotheses (Verbose enforces the split: `Fix` rejects Props, `Assume` rejects data) | covered; forces the elements/proofs distinction the game teaches |
| `exact`, `assumption` (116, 8) | `We conclude by h`, `We conclude by hypothesis` (`exact` → `apply;done` → `rw;rfl` → `linarith`) | covered, works on data goals too |
| `apply` (44) | `We apply f`, `By h it suffices to prove that P` | covered |
| `have` (18) | `Fact h : P from …` / `by …` / `since …`; `Claim` | covered (one-line forms work in typewriter mode) |
| `let` (6) | `Set x := …` | covered, needs checking for data |
| `constructor` on `∧`/`↔` (part of 51) | `Let's first prove that P` / `Let's now prove that Q` | covered via `configureAnonymousGoalSplittingLemmas And.intro Iff.intro` |
| `constructor` on `×`, `Σ`, `Equiv` structures | none; `goalBlocker` is typed `Prop`, so goal splitting fails on `Type` goals | **gap** |
| `left`/`right` on `∨` (17) | `Let's prove that P` picks the disjunct (`orTac`) | covered |
| `left`/`right` on `⊕` | none | **gap** |
| `rcases`/`cases` on `∧`, `∃`, `∨` (49 total) | `By h we get (hp : P) (hq : Q)`, `Since … we get x such that …`, `We discuss depending on whether P or Q`, `We proceed using h` | covered |
| `cases`/`match` on `Bool`, `ℕ`, `⊕`, `×` data | `We proceed depending on b` is `cases`, probably fine for Bool/ℕ; nothing for naming components of a pair or sum | **gap** for `⊕`/`×` and for defining functions by `match` |
| `exfalso`, `absurd`, `False.elim`, `Empty.elim` | `Let's prove it's contradictory`, then `We conclude by h applied to hp` | covered for Props; `Empty` on data needs a phrase |
| `rfl` (51) | `We conclude by rfl`; `We compute` is `ring_nf`/`norm_num`/`dsimp`, not reliable for the game's definitional `rfl` levels | covered |
| `rw` (18) | `We rewrite using h` / `← h` | covered |
| `use` (15) | `Let's prove that x works` | covered |
| `ext` (6) | `By funext it suffices to prove that ∀ x, f x = g x` | plausible, verify |
| `induction n with k hk` (5) | `Let's prove by induction H : ∀ n, P n` (player must state the motive; inductive step is reverted, so `Fix k` and `Assume hk` follow) | covered, different pedagogy |
| `Classical.em`, `byContradiction` | `We discuss depending on whether P or ¬P` (`Classical.em` is a configured case-splitting lemma), `Assume for contradiction h : ¬P` | covered; note `allowProvingNegationsByContradiction` is off by default |

So roughly two thirds of the levels map onto existing phrases and one third needs **new
Verbose-style construction phrases** (pairing, injections, case analysis on data with named
components, defining a function by cases, eliminating `Empty`, maybe 6–10 macros). Verbose is a
library of ordinary Lean macros/elabs with a documented extension mechanism: its own `syntax`
wrapper splits multi-word phrases into tokens (`splitMolecule` in `Verbose/Tactics/Common.lean`)
and `register_endpoint`/`implement_endpoint` for multilingual messages, so the game can define
phrases in the same style in its `Game/Metadata/Tactic/` directory, exactly as it already defines
custom `constructor`, `rw`, `use`, `induction`.

**The real risk is curricular, not technical.** The game's thesis is that elements and proofs
follow the same rules, and stock Lean's `intro`/`exact`/`constructor` make that visible. Verbose
deliberately hides it behind distinct English registers (`Fix` vs `Assume`, "prove" vs whatever
is chosen for "construct"). Recommendation: lean into it. Keep the distinction in the phrases
and make the parallel explicit in Conclusions ("notice `Fix` and `Assume` changed the goal in the
same way"). A verbose game that is restricted to the propositional worlds would gut the game.

**Technical incompatibilities found (all workable):**

1. **Environment-extension name clash.** Verbose registers its configuration extension under the
   name `gameExt` (`Verbose/Infrastructure/Extension.lean:154`, same at `v4.23.0` and `master`),
   and `GameServer/EnvExtensions.lean:451` registers `gameExt` too. Importing both fails with
   "invalid environment extension, 'gameExt' has already been used". math-atlas-lean solved it by
   vendoring Verbose with a one-line rename to `verboseConfigExt`. Better: fork, apply the rename,
   PR it upstream (no issue or PR about this exists yet in `PatrickMassot/verbose-lean4`).
2. **Inventory check is word-by-word.** `GameServer/Inventory.lean:117` `collectUsedInventory`
   records every alphabetic atom of the proof as a "tactic" (except `with fun at only by
   generalizing using skip if then else clear`), and Verbose splits "We conclude by" into the
   atoms `We`, `conclude`, `by`. So the game must declare `NewTactic «We» «Let's» «Fix» «Assume»
   «Since» «By» «Fact» …` and `NewHiddenTactic «conclude» «applied» «to» «prove» «that» «works»
   «get» …` (math-atlas does precisely this). Inventory tiles named "We" and "Let's" are awkward;
   the `TacticDoc` for each leading word can list its phrases. A later upstream improvement to
   lean4game (match by syntax kind or allow multi-word `TacticDoc` names) would fix this properly.
3. **No widget support in lean4game.** The client depends only on `@leanprover/infoview-api`
   (types), not on the infoview renderer, so Verbose's point-and-click suggestion panel
   (ProofWidgets, `Verbose/Tactics/Widget.lean`) will not appear. The `help` tactic emits
   `TryThis.addSuggestions`, which lean4game shows as plain info text without click-to-insert.
   Set `disableWidget` in the game. Acceptable for phase 1; this is the natural target of the
   "reimagined UX" (see Part C), and it is what lean4game issue #277 asks for.
4. **Typewriter mode is one line per step.** Verbose `Calc` and `Fact … by <indented block>` need
   editor mode (math-atlas tells players to switch). Prefer one-line forms (`Fact h : P from …`,
   `… since …`), avoid `Calc`. The current game already lives with this constraint.
5. **Version alignment of three projects.** Tags must agree across lean4game
   (v4.22, 4.23, 4.28, 4.29, 4.29.1, 4.31, 4.33.1, 4.35), Verbose (v4.18–4.25.2, 4.29, 4.30,
   4.31; `master` is at v4.31.0), Mathlib and lean-i18n. Intersection today: v4.23.0, v4.29.0,
   v4.31.0. Verbose is the laggard, so the verbose game can only bump to versions Verbose has
   tagged. See "Lean version" below: nothing forces v4.23.0, and v4.31.0 is recommended.
6. **Heavier imports.** Verbose pulls `Mathlib.Data.Real.Basic`, `Linarith`, `Ring`, `Abel`.
   The original imports only slivers of Mathlib. Expect slower level start on the server
   (lean4game issue #328 is about Mathlib-heavy games); measure in the spike.
7. **Reserved words.** `We Fix Set By Since Fact Calc Assume Let's` become keywords; connective
   words stay usable as identifiers. The game's identifiers (`P Q A B f g h a b n x`) are fine.
   Verbose issue #12 documents the general clash problem for translations.
8. **Scoped syntax does not reach the player (found in the spike).** lean4game parses the
   player's `Runner … := by …` document before it re-applies the level's `open` declarations,
   so Verbose's `scoped` Named phrases (`Assume h : P`, `Fact h : …`, `Let's prove by
   induction H : …`) are unavailable to players even with `open Verbose.Named` in the level
   file. Fix used in the spike: re-declare those phrases globally in the game
   (`Game/Metadata/Tactic/NamedPhrases.lean`, ~25 lines delegating to Verbose's elaborators).
   Upstream proposal for lean4game: emit the level's `open`s in the document header
   (`verbose-game-spike/ISSUE_DRAFT_lean4game_scoped_syntax.md`).
9. **Verbose displays implications as `P ⇒ Q`.** Its delaborator in
   `Verbose/Tactics/Notations.lean` changes how `→` between propositions prints, and `help`
   messages use `⇒`. The game can put Lean's default back with a three-line delaborator
   (`Game/Metadata/Tactic/Arrow.lean` in the spike); whether to keep `→` (the game's
   Curry–Howard theme) or adopt `⇒` is Emily's pedagogical call.
10. **Verbose is opinionated.** `Let's prove that P` must restate the goal exactly (up to defeq),
   `Assume` must name the hypothesis type, negations may not be proved by contradiction unless
   configured. More typing in a browser (lean4monaco supports `\and`-style unicode input), but
   it is the intended pedagogy. Hints must give exact phrases.

### A2. Is it reasonable to link the two games as described?

**Yes, with a clear ceiling on what "automatic" can mean.** The two games must be separate
GitHub repositories: lean4game identifies and imports a game as `owner/repo` from that repo's
`build-for-server-import` artifact (`relay/src/import.ts`), one game per repo, no subdirectory
or branch selection.

What propagates automatically through a git merge from the original:
- world graph (21 `Dependency` edges), level order, titles, images, cover text;
- every `Statement` (identical mathematics), statement docstrings, `TheoremDoc`/`DefinitionDoc`;
- the tactic-neutral prose: ~120 of 176 Introductions, ~119 of 159 Conclusions, ~148 of 361 hints.

What cannot propagate and must be authored once per level in the verbose repo:
- all 159 proofs;
- all 19 `TacticDoc`s and every `NewTactic` line;
- ~213 hints and ~56 level Introductions that name a tactic.

Expected steady state: a new or changed level upstream arrives as a PR in the verbose repo with
the shared parts merged and the proof/hint lines in conflict, which a human resolves by writing
the verbose version. Pure prose or statement fixes merge with no human work. A CI parity check
guarantees the two games never silently diverge mathematically.

2. The one-line `gameExt` rename goes to Verbose as a PR Emily opens; until merged the game

3. New standalone repo `emilyriehl/VerboseReintroductionToProofs`, seeded from the original's

5. UX work as a later, separable phase: a lean4game client fork rendering Verbose suggestions
   as clickable chips in the typewriter, self-hosted or upstreamed.

### A4. Lean version: nothing forces v4.23.0; target v4.31.0

Why the original is on v4.23.0: only its own pin (GameSkeleton's template is still at v4.23.0,
as are NNG4 and STG4). The GameSkeleton lakefile derives every dependency tag from the toolchain
string, so any version works where GameServer, Mathlib and lean-i18n all have a `v4.X.Y` tag.
adam.math.hhu.de runs each game with the game's own GameServer binary, and it already hosts a
v4.31.0 game (hhu-adam/Robo), so mixed versions on the server are fine.

The newest version all of lean4game, Verbose, Mathlib and lean-i18n share is **v4.31.0**
(lean4game has v4.33.1 and v4.35.0 tags, Verbose does not). Reasons to start the verbose game
there rather than v4.23.0:
- Verbose `master` is at v4.31.0, so any phrases Emily proposes upstream are developed and tested
  against the version Patrick is working on, and his fixes (e.g. the Oct 2026 code-action change)
  are available.
- Newer GameServer (`LevelScope`, inventory and hint fixes in lean4game #499, #507, #509, #518).
- One fewer bump to do later; Lean 4.23 is a year old.

Consequences:
- `lean-toolchain`, `lakefile.lean` (lean4game #518 restructured it; use hhu-adam/Robo's current
  lakefile as the v4.31.0 reference, not GameSkeleton `main`) and `lake-manifest.json` will
  permanently differ from the original. The sync workflow resolves those three paths as "ours"
  after each merge (`git checkout --ours` + a `.gitattributes` note), so this costs nothing.
- The original's custom tactics (`Metadata/Tactic/{Rw,Use,Induction,Constructor}.lean`) copy
  Mathlib internals and may need small edits at 4.31; the verbose game replaces most of them.
- Optional and separate (needs permission): bump the original to v4.31.0 too, which would keep
  the two repos in lockstep. Not required for anything in this plan.

Fallback: if the spike hits a v4.31.0-specific problem, do the spike at v4.23.0 and bump later.

### Phase 3: Linking automation (in the verbose repo only)

`.github/workflows/sync-upstream.yml`
- Triggers: weekly cron, `workflow_dispatch`, and optionally `repository_dispatch` sent by the
  original repo's build workflow (that last trigger needs a one-line addition to the original's
  `build.yml` plus a token; only with explicit permission).
- Steps: checkout `main` with full history; `git remote add upstream
  https://github.com/emilyriehl/ReintroductionToProofs`; `git fetch upstream`;
  `git merge --no-ff upstream/main`.
  - Always keep `lean-toolchain`, `lakefile.lean`, `lake-manifest.json` from the verbose side
    (`git checkout --ours -- <paths>` after the merge), since the two games run different Lean
    versions.
  - Clean merge: push branch `sync/upstream-<shortsha>`, update `UPSTREAM_COMMIT`, open a PR
    (`peter-evans/create-pull-request`), let the build + parity jobs run; auto-merge if green
    (optional).
  - Conflicts: `git diff --name-only --diff-filter=U` → open/update one issue listing conflicted
    files and the upstream commit range, with the resolution recipe
    (`git fetch upstream && git merge upstream/main`, write the verbose proof/hints, push).

`.github/workflows/parity-check.yml` + `scripts/check_parity.py` (Python, stdlib only)
- Clone upstream at `UPSTREAM_COMMIT`; for every `Game/Levels/<World>/L*.lean` on both sides
  extract `World`, `Level`, `Title`, the `Statement … :=` header (statement name, binders,
  type; whitespace-normalised) and the statement docstring; compare `Game.lean` `Dependency`
  lines and each world file's level import list.
- Fail with a readable diff when a statement, level set or world graph differs, except for an
  explicit allowlist file (`parity-allowlist.txt`).
- Runs on every PR and push; this is the guarantee that both games present the same mathematics.

Optional, in the original repo (needs permission, can wait): a writing convention that keeps
tactic-specific sentences in their own paragraph at the end of Introductions and Hints, so
line-based merges touch different hunks; and a README pointer to the verbose game.

Alternative considered and not recommended initially: an overlay generator (upstream as a git
submodule + per-level verbose fragments + a script that regenerates level files). It isolates
verbose-specific content cleanly but makes the verbose repo a non-standard lean4game project
that outside contributors cannot edit directly. Revisit only if merge conflicts become the
dominant cost.

- Phase 2: after each world is imported to adam, Emily plays it there before the next world is
  ported; issues are filed in the verbose repo's tracker with a `ux` label so they are kept apart
  from content bugs. A short checklist per world: typing effort per level, hint clarity, whether
  the player can tell what to type next without the hint, mobile layout.
- Phase 4: the client changes (suggestion chips, per-phrase tiles) get a before/after playtest on
  the same two worlds, ideally also with one or two people from the target audience.

### Phase 4: Second website and reimagined UX (separable, after content exists)

Facts: adam hosting costs nothing and reuses the public import flow. Self-hosting
(`doc/hosting.md`) needs a Linux box with nginx, node/pm2, bubblewrap, elan; the relay serves
games from `games/<owner>/<repo>` and launches each player's Lean process from the game's own
`.lake/packages/GameServer` binary, so a self-hosted instance can also run a patched GameServer.
The client is React 18 + jotai/redux + `lean4monaco`; typewriter UI lives in
`client/src/components/editor/typewriter/`.

Recommended path:
1. Phase 2 game on adam first (same UX as today).
2. Fork `lean4game`, change only the client: render `TryThis` suggestions (what Verbose's `help`
   emits) as clickable chips above the typewriter command line, auto-run `help` after each step,
   and show inventory tiles per phrase rather than per leading word. This is the cheapest way to
   get most of Verbose's point-and-click experience and is upstreamable (it is what lean4game
   issue #277 requests).
3. Self-host that client (JHU or a VPS) pointing at the same game artifact, or upstream it so
   adam gets it. Deeper redesigns (progress model, mobile layout, replacing Monaco) only after
   that.
